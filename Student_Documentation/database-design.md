# Database Design

## 1. Overview

The Multi-Format Document RAG System uses **MongoDB Atlas** as its primary database.

MongoDB is used for:

- User data
- Conversations
- Chat messages
- Document metadata
- Document chunks
- Vector embeddings
- Semantic vector search

The database also uses **MongoDB Atlas Vector Search** to retrieve document chunks that are semantically relevant to a user's question.

                                  4. Users Collection

The users collection stores registered user accounts.

Conceptually, a user document contains information such as:

{
    _id,
    username,
    password_hash
}

The password is not stored in plain text.

Instead, the application stores a securely hashed password.



4.1 User Identity

Each user is identified using a unique user identifier.

The authenticated user's ID is used throughout the application to associate:

Conversations
Messages
Documents
Document chunks

with the correct user.



5. Conversations Collection

The conversations collection stores individual chat sessions.

A conversation belongs to a specific user.

Conceptually:

{
    _id,
    user_id,
    title,
    created_at,
    updated_at
}

The user_id identifies the owner of the conversation.

5.1 Conversation Example

A user can have multiple conversations:

User A
│
├── Conversation 1
│
├── Conversation 2
│
└── Conversation 3

Each conversation has its own identifier.

For example:

User A
│
├── conversation_id: 101
├── conversation_id: 102
└── conversation_id: 103

The actual MongoDB identifiers are generated by the application/database.

6. Conversation Titles

When a new conversation starts, the first user question can be used to generate the conversation title.

For example:

User Question:
"What is Internet of Things?"

The conversation can be displayed in the sidebar using a shortened title such as:

What is Internet of Things?

The title is limited in length to keep the conversation sidebar clean.

8. Document Chunks Collection

9. Document ID

Each uploaded document receives its own document_id.

For example:

Conversation 1
│
├── Document A
│     document_id: A
│
└── Document B
      document_id: B

The document_id allows individual uploaded documents to be identified even when multiple documents belong to the same conversation.

10. Multiple Documents Per Conversation

A single conversation can contain multiple documents.

For example:

Conversation: RAG Research
│
├── RAG.pdf
├── VectorSearch.pdf
└── LLM.pdf

The chunks from all of these documents can be stored in the document_chunks collection.

Each chunk retains its original document information.

Example:

Chunk 1
│
├── document_id: RAG.pdf

└── conversation_id: Conversation 1

Chunk 2
│

15. User-Level Data Isolation

The application is designed to prevent users from accessing each other's documents.

Consider two users:

User A
│
└── Conversation A
      └── Document A


User B
│
└── Conversation B
      └── Document B

When User A asks a question, the vector search is restricted to User A's data.

The retrieval filter uses:

user_id

This prevents User B's document chunks from being retrieved for User A.

16. Conversation-Level Data Isolation

The system also isolates documents between conversations belonging to the same user.

For example:

User A
│
├── Conversation 1
│     └── Python.pdf
│
└── Conversation 2
      └── Java.pdf

When the user asks a question in Conversation 1, the retrieval is restricted using:

conversation_id

Therefore, the system does not retrieve Java document chunks from Conversation 2 when answering questions in Conversation 1.

user_id

18. Why document_id Is Also Stored

The document_id is not primarily used as the main retrieval boundary.

Instead, it identifies the specific source document that a chunk belongs to.

For example:

User A
│
└── Conversation 1
      │
      ├── Document A
      │     ├── Chunk 1
      │     ├── Chunk 2
      │     └── Chunk 3
      │
      └── Document B
            ├── Chunk 1
            ├── Chunk 2
            └── Chunk 3

This allows the system to retrieve chunks across multiple documents in the same conversation while still knowing the original source of each chunk.

22. Conversation Deletion

When a conversation is deleted, its associated data is also removed according to the application's deletion logic.

The deletion process includes:

Delete Conversation
       │
       ├── Delete Messages
       │
       ├── Delete Document Chunks
       │
       └── Delete Conversation

This prevents orphaned conversation data from remaining in the database.

23. Persistent Chat History

Because messages are stored in MongoDB, conversations remain available after the user leaves the application.

For example:

Today:

Conversation 1
├── User: What is RAG?
└── AI: RAG stands for...


Later:

Conversation 1
├── User: What is RAG?
├── AI: RAG stands for...
├── User: Why is vector search used?
└── AI: Vector search is used...

This enables persistent chat sessions rather than temporary browser-only conversations.

24. Database Security Considerations

The application follows several security practices:

Passwords are stored as hashes rather than plain text.
Authentication uses JWT tokens.
Protected endpoints require authentication.
Conversation ownership is validated.
Document retrieval is restricted by user and conversation.
Database credentials are stored in environment variables.
API keys are stored in environment variables.
Sensitive credentials should not be committed to Git.

The .env file should remain excluded through .gitignore.

25. Database Design Principles
User Ownership

Every conversation and document chunk is associated with a user.

Conversation Isolation

Documents are scoped to individual conversations.

Persistent State

Messages and conversations are stored in MongoDB.

Source Traceability

Document chunks retain document names and chunk indexes.

Vector Search

Embeddings are stored alongside document chunks for semantic retrieval.

Modular Data Model

Different responsibilities are separated into logical collections.
